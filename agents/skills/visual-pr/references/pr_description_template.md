# PR description

Include relevant ticket or plan links above the sections when available.

## Why the change

Exactly one sentence explaining the problem and what this change makes possible.

## Special things to note

One to three bullets for reviewer-relevant warnings, migrations, constraints, or surprising decisions. Use `- None.` if there are none.

## Change outline

Use the smallest set of structural views that explains the implementation. Choose from contracts, types, pseudocode, file or component trees, and control or data flow. Show only what changed. Prefer a focused `diff` for an existing shape and a complete block for a mostly new shape. Keep the outline compact and readable without the codebase open.
